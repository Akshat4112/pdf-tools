# PT-CORE-011 — Images to PDF interface

The `/pdf-tools/images-to-pdf/` route now opens the live JPG/PNG workspace. The catalog's enabled flag is set only with this interface; conversion uses the PT-CORE-010 engine unchanged.

## User workflow

1. Choose or drop local static JPG/PNG images. Accepted types and the engine limits are visible before selection: 300 images, 50 MiB total encoded bytes, 16 million pixels per image and 25.6 million pixels total.
2. File names are sanitized and rendered as text. Damaged, unsupported or oversized files appear with an explanation and Remove. Other valid files remain usable; the final review explicitly states that files marked with errors are left out.
3. Move images earlier/later using the file-row buttons with pointer, touch, Enter or Space. Remove individual files or append more images. Selection order becomes page order, with one valid image per page.
4. Choose A4, Letter or original image sizing; auto/portrait/landscape paper orientation; margins in points; and Fit entire image or Fill page (crop edges). Original size requires auto orientation and exposes 96/150/200 DPI. Switching to Original resets paper orientation to Auto. Blank, negative, nonfinite or excessive margins disable conversion with a useful message.
5. Review the page previews, dimensions and output order. There are at most eight canvases mounted; Previous/Next navigates the selection without changing its order. Auto orientation follows camera EXIF, including mirrored orientations. Transparent areas and margins are explicitly white.
6. Create PDF. Progress and cancellation use the shared job panels. The engine independently verifies output count and page geometry before the result can be downloaded.
7. Repeated Download uses the same tracked object URL. Clear files discards the selection/previews/output while keeping page preferences. Start over and Run again with other files restore the default settings. Back or Continue to another tool disposes the workspace.

## Preview and export agreement

Both paths call the engine's `readImageMetadata` and `planImagePage`. The canvas renderer applies the plan's affine image matrix and margin clip directly, accounting for the opposite vertical coordinate directions in PDF and Canvas.

Native browser image decoding can auto-apply EXIF. A temporary preview-only copy has its JPEG APP1 EXIF or PNG eXIf removed before decoding, and then the shared plan applies the single intended orientation. The original bytes are preserved for export. Source images are never canvas re-encoded.

Preview decoding is sequential and requests a small bitmap within 560 × 720 pixels. Every bitmap is closed on completion/failure/late disposal. The paper canvas is bounded to a 280 × 360 pixel envelope. Canvases are cleared when options change, pagination changes, processing begins, files are cleared or the route exits. Header metadata is cached with each selected file so settings changes and reorder do not repeat CRC/header scanning.

Layout agreement does not promise full color-profile fidelity; the screen discloses that profiles may look different in the PDF. Chromium mobile emulation verifies responsive interaction, not physical low-memory mobile behavior; the later memory benchmark remains necessary.

## File reading and lifecycle

The shared picker now checks file sizes before calling `arrayBuffer`, supports optional selection byte/count limits and honors the tool's custom limits label. Batch limits reject the incoming batch before reading, while a single file above the per-file limit gets an error row without allocating its bytes. Invalid names use the existing sanitizer, and error rows preserve the original reported file size.

File reads carry a generation token. A newer selection, reorder, removal, Clear files, changed parent selection or unmount invalidates pending reads. File-read failures are caught and shown in the list. Late reads cannot refill a cleared selection. This guard also protects existing tools using the same picker.

The interface tracks jobs with `JobSession`, cancels them on reset/exit and checks both mount state and active job identity before accepting progress/completion callbacks. A cancelled engine may finish a current native decode, but its bitmap is closed and no partial or late result is shown. Output URLs are revoked and output bytes dropped on reset/exit. Files, names, plans, images and generated bytes stay in memory; there is no server upload, URL encoding or persistent browser storage.

## Verification

From `app/`:

```sh
npm ci
npm run lint
npm test
npx tsc -p tsconfig.test.json --noEmit
npm run build
npx playwright install --with-deps chromium
npm run test:pages-ui
npm run test:images-engine
npm audit --omit=dev --audit-level=high
```

`test:pages-ui` includes the new interface and existing page-tool regressions, for desktop and mobile Chromium. `test:images-engine` retains the engine's eight render checks. On constrained machines use `npm test -- --maxWorkers=2`; `PDF_TOOLS_CHROMIUM_PATH` can select a preinstalled browser.

Interface coverage:

- Mixed JPG/PNG EXIF orientations, including mirrors and transparency: compare actual preview pixels with the independently rendered downloaded PDF, plus check original page dimensions.
- A4/Letter, auto/portrait orientation, contain/cover and margins: compare preview/output pixels, verify the white margins and expected page sizes, and confirm settings/canvases fit the viewport.
- Keyboard reorder, removal, append, bounded pagination and Clear files: exported widths prove the visible order.
- Malformed, unsupported and oversized images; invalid/blank margins; excessive file count: valid files recover without an unverified result.
- Oversized files are rejected before reading; pending reads released after clear/exit cannot restore old files.
- Repeated downloads reuse one URL; reset/exit revoke it; held native decode followed by cancellation/reset cannot publish late output; a fresh conversion succeeds afterward.

The test-only independent PDF.js reader is supplied through Playwright routing and does not enter the production build. Only synthetic images are used, with no document-bearing CI artifact uploads. Optional local screenshots (`PDF_TOOLS_VISUAL_DIR`) were inspected for desktop/mobile layout.
